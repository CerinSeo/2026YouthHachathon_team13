# ARCHITECTURE - 빙빙제로

## 1. 목적과 최종 결정

이 문서는 6시간 해커톤에서 구현할 최종 시스템 경계를 정의한다. 이전 자료에
등장한 FastAPI, OpenRouteService, TMAP 보행 경로, 사전학습 AI 모델은 최종안이
아니다. 승인된 구조는 다음과 같다.

- React 19 + TypeScript + Vite responsive web
- Leaflet + OpenStreetMap 지도
- Cloudflare Worker 기반 비밀키 보호·외부 API 중계
- 브라우저 `src/core`의 데이터 검증·위험 추정·경로 계산
- Geofabrik South Korea PBF에서 빌드한 서울 공통 OSM 보행 타일
- TMAP 장소 검색
- Open-Meteo 실제 현재·예보·과거 기상
- 학습 모델이 아닌 버전이 있는 규칙 기반 결빙 위험 추정

API 키가 준비되어 있어도 공급자의 역할과 계산 책임은 이 문서대로 유지한다.

## 2. 설계 원칙

- 서울 전역에 같은 데이터 처리·경로 규칙을 적용한다.
- 일반 경로와 추천 경로는 동일한 보행 그래프와 거리 계산을 사용한다.
- 자동차용 그래프나 자동차 전용·보행 금지 간선을 보행 경로에 섞지 않는다.
- 비밀키는 Worker에만 두며 브라우저 번들·로그·응답에 노출하지 않는다.
- 외부 자료 실패를 0값이나 낮은 위험으로 바꾸지 않는다.
- 실제 데이터, 계산 결과, 사용자 표현을 분리한다.
- 같은 데이터 버전과 선택 시각으로 결과를 재현할 수 있게 한다.
- P0 종단 흐름을 우선하고 P1·P2 때문에 완성을 지연하지 않는다.

## 3. 시스템 구성

```text
TMAP / Open-Meteo / KMA(P1)
             │
             ▼
Cloudflare Worker
  - API 키 보관
  - 허용 endpoint만 중계
  - timeout·오류 정규화
             │
             ▼
React 19 + TypeScript + Vite
  ├─ UI: Material 3 + Leaflet
  └─ src/core
      ├─ 입력·서울 범위 검증
      ├─ 정적 보행 타일 로딩·SHA-256 검증
      ├─ 일반 최단 경로
      ├─ 실제 기상 정규화
      ├─ 결빙 위험 예상구간
      ├─ 계단·경사·위험 간선 제외
      └─ 추천 경로·추가시간 계산
             ▲
             │
정적 서울 데이터 자산
  - index.json
  - 0.04° 보행망·건물 타일
  - 출처·기준 시각·해시
```

서버는 전체 경로 계산을 대신하지 않는다. Worker는 비밀키가 필요한 외부 호출과
오류 정규화만 담당하고, 핵심 분석은 `src/core`에서 실행한다.

`npm run dev`는 로컬 Node 전송 계층으로 같은 API 처리기를 호출한다. 이 환경의
Cloudflare 모의 런타임에서는 외부 호출이 실패했다. `npm run build`는 배포용
Worker와 정적 앱을 빌드하며 빌드 결과에 로컬 비밀 설정 파일을 싣지 않는다.

  core/

    graph/             보행 그래프·스냅·Dijkstra
    weather/           정규화·시간 선택·상태
    risk/              규칙 기반 위험 추정

    contracts/         public 타입과 오류
  services/            Worker·정적 자산 호출

같은 책임의 모듈을 다른 경로에 중복 생성하지 않는다.

## 5. 서울 보행망 사전 빌드

이 저장소에는 해커톤용으로 제공된 Geofabrik 파생 타일 108개가 들어 있다.
`scripts/build-seoul-walk.py`는 원본 PBF를 다시 내려받는 대신 제공본의 범위,
출처와 SHA-256을 검증해 배치한다. 앱은 v1 압축 파일을 직접 해독한다.
인덱스의 사각형은 타일 조회 범위이며, 입력이 서울에 속하는지는 같은 데이터
폴더에 있는 OpenStreetMap 행정 경계로 검증한다.

### 5.1 입력과 범위

- 입력: Geofabrik `south-korea-latest.osm.pbf`
- 서울 공통 범위: `[남, 서, 북, 동] = [37.39, 126.73, 37.72, 127.20]`
- 타일 크기: 위·경도 `0.04°`
- 출력: `index.json`과 필요한 JSON 타일
- 인덱스에는 원본 URL, 다운로드 시각, OSM 기준 시각, 타일 형식 버전,
  각 파일 크기와 SHA-256을 기록한다.
- 원본 PBF는 저장소에 커밋하지 않는다.

### 5.2 포함할 보행 way

기본 포함 태그는 다음과 같다.

- `highway=footway|pedestrian|path|steps`
- 보행이 명시적으로 허용된 `highway=cycleway`

다음을 제외한다.

- `foot=no|private` 또는 동등한 접근 제한
- 자동차 전용·고속도로
- 필요한 참조 노드가 빠진 way
- 통과할 수 없는 barrier와 횡단 제한

way의 노드 순서를 보존하고 `oneway:foot`, 보행 방향, 접근 태그를 반영한다.
간선 ID는 `way/<osm-way-id>:<연속쌍-index>`로 만든다. 단순히 자동차 도로의
중심선을 보행 경로로 사용하지 않는다. 별도 보도 형상이나 명시적 보행 way가
없어서 연결되지 않는 곳은 임의 직선으로 잇지 않고 연결 실패로 처리한다.

### 5.3 타일 내용

- 보행 way와 참조 노드
- 간선 ID, 방향, 길이, 접근 상태
- 계단·경사·램프·교량·실내·터널 관련 태그
- 닫힌 건물 외곽선과 유효한 양수 높이
- 출처·라이선스·타일 기준 시각

계단·경사·건물 높이가 없으면 0이나 없음으로 보충하지 않고 `unknown`으로 둔다.

## 6. 입력과 장소 검색

- 내부 좌표는 WGS84 `[longitude, latitude]`다.
- TMAP은 장소 검색에만 사용한다.
- 장소 좌표는 보행자 출입구 → 일반 출입구 → 중심점 순으로 유효한 값을 선택한다.
- 검색 결과, 현재 위치, 지도 선택 중 하나로 출발지와 목적지를 정한다.
- 두 좌표 모두 서울 범위 안인지 확인한다.
- 각 좌표는 최대 80m 이내의 가장 가까운 보행 노드에 연결한다.
- 스냅 실패, 같은 노드 연결, 서울 밖 입력은 서로 다른 오류로 반환한다.

## 7. 일반 경로

- 간선 길이는 Haversine 거리로 계산한다.
- 동일 보행 그래프에서 거리 기준 Dijkstra 최단 경로를 계산한다.
- 결과에는 간선 ID 순서, GeoJSON 형상, 거리, 예상시간을 포함한다.
- 기본 보행속도는 `1 m/s`다.
- 시간에는 보행망 연결 전 접근 거리와 신호 대기를 포함하지 않는다.
- 경로가 없으면 직선이나 임의 경로를 생성하지 않는다.

## 8. 기상 구역과 위험 추정

- 경로와 후보 우회 범위를 덮는 타일의 중심을 기상 조회 지점으로 사용한다.
- 간선은 중점이 속한 조회 구역의 선택 정각 기상을 적용한다.
- 내부 시간 비교는 epoch 또는 timezone이 포함된 ISO 8601을 사용하고 UI는 KST로 표시한다.
- 현재·예보는 Open-Meteo Forecast, 과거 재생은 Historical Forecast 또는 명시한
  Single Run/AIFS 자료를 사용한다.
- 선택 정각의 적용 기온이 `0°C 이하`이고 직전 6시간에 실제 양의 강수 또는
  강설 근거가 하나 이상 있을 때 재결빙 조건으로 분류한다.
- 6시간 창의 필수 시간이 누락되면 0으로 합산하지 않고 `UNKNOWN`으로 둔다.
- 재결빙 조건이 있는 구역에서 실외 보행교와 검증된 그늘 구간을 결빙 위험
  예상구간으로 만든다.
- P0의 그늘은 OSM 건물 높이 기반 투영을 사용한다. 지형 가림은 P1이다.
- 위험 계산 방식에는 버전 `risk-rule-v1`을 기록한다.

상세 필드·우선순위·결측 처리는 `DATA_AND_AI.md`를 따른다.

## 9. 추천 경로

다음 간선의 합집합을 회피 집합으로 만든다.

- 실제 기상과 공간 근거로 판정된 결빙 위험 예상 간선
- `highway=steps`, `stairs=yes`, `steps=yes`, 양의 `step_count` 간선
- 유효한 0이 아닌 `incline`, 방향성 incline, `footway=ramp`, `ramp=yes|wheelchair` 간선

추천 경로는 회피 집합을 그래프에서 제외하고 같은 시작·도착 노드 사이의 거리
기준 최단 경로를 다시 계산한다. 비용 점수로 위험을 숨기지 않고 P0에서는 명시적
제외 방식을 사용한다.

- 일반 경로에 회피 간선이 없으면 `same_as_baseline`을 반환한다.
- 연결이 끊기면 `unavailable`과 이유를 반환한다.
- 추천 결과의 제외 간선 수가 0인지 후검증한다.
- 일반·추천 경로의 시간은 모두 `거리 / 1m/s`로 계산한다.
- 추가시간은 `추천시간 - 일반시간`이다.

## 10. Worker 경계

Worker는 다음만 담당한다.

- `TMAP_APP_KEY`, `KMA_API_KEY`, `KMA_GRID_API_KEY` 등 비밀 저장
- 허용한 외부 host·path로만 요청
- 입력 길이·좌표·날짜 범위 검증
- timeout과 공급자 오류 정규화
- 키·원본 오류 stack·민감 header 제거
- 짧은 캐시와 중복 요청 병합

사용자 계정, 경로 이력, 검색 이력을 저장하지 않는다. 외부 응답을 24시간 이상
보존해야 할 경우 공급자 약관을 먼저 확인한다.

## 11. P0·P1·P2 경계

### P0 - 반드시 구현

- TMAP 장소 검색
- 서울 보행 타일 빌드·검증·로딩
- 일반 Dijkstra 경로
- Open-Meteo 현재/과거 실제 기상
- `risk-rule-v1`과 건물 그늘·보행교 위험 구간
- 계단·경사·위험 간선 제외 추천 경로
- 두 경로·추가시간·자료 상태 UI
- 양재 고정 시나리오와 서울 복수 생활권 검증

### P1 - P0 이후

- 기상청 500m 분석 → 초단기 → 단기 → Open-Meteo 우선순위
- Copernicus GLO-30 기반 지형 가림
- AWS 관측 강수 보강
- 고대비 옵션과 더 정밀한 접근성 QA

### P2 - 시간 여유가 있을 때

- 서울시 강우·제설·열선 자료 교차 검증
- 캐시·동시 요청 최적화
- 그늘·지형 계산 성능 개선
- 운영 모니터링

P1·P2가 없어도 P0를 가짜 데이터로 대체하지 않는다.

## 12. 오류 경계

| 오류 | 처리 |
|---|---|
| 장소 검색 실패 | 입력 오류, 임의 좌표 금지 |
| 서울 밖 좌표 | 지원 지역 밖 상태 |
| 타일 또는 해시 실패 | 경로 계산 중단 |
| 보행망 스냅 실패 | 연결 실패 이유 반환 |
| 일반 경로 없음 | 두 경로 모두 생성하지 않음 |
| 기상 자료 부족 | 일반 경로만 표시 가능, 추천은 `not_evaluated` |
| 추천 경로 없음 | 일반 경로와 추천 불가 상태 반환 |
| 외부 API 실패 | 공급자 실패와 재시도 안내 |
| 계산 예외 | geometry·시간 임의 생성 금지 |

## 13. 라이선스와 출처

- OSM 데이터와 지도에는 OpenStreetMap 기여자 표시와 ODbL 링크를 제공한다.
- Geofabrik 다운로드 URL과 원본 기준 시각을 인덱스에 남긴다.
- Open-Meteo 자료는 사용 조건과 출처를 기록한다.
- TMAP 응답은 약관의 저장 기간을 넘겨 저장하지 않는다.
- 생성 타일을 배포할 때 OSM 파생 데이터의 라이선스 의무를 유지한다.

## 14. 완료 조건

- 서울의 서로 다른 생활권에서 같은 그래프 규칙이 동작한다.
- 일반·추천 경로가 동일한 승인 보행 그래프를 사용한다.
- 결과 간선에 자동차 전용·보행 금지 간선이 없다.
- 실제 기상 출처·기준 시각·상태를 추적할 수 있다.
- 위험 입력이 추천 경로에 실제로 반영된다.
- 자료 부족과 낮은 위험을 구분한다.
- 내부 기상값·점수·임계값이 UI에 노출되지 않는다.
